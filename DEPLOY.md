# Deploying esp-atlas

esp-atlas ships as a **single Vercel deployment**: the Next.js frontend
(`apps/web`) and the FastAPI backend (`apps/api`, `esp_atlas_api.main:app`)
same-origin, with the backend served as a Vercel Python serverless function
under `/api`.

## Layout

The Vercel project's **Root Directory is `apps/web`** — Vercel detects Next.js
there and bundles only files under it, so the Python function and everything it
needs are co-located inside `apps/web`:

```
apps/web/
  vercel.json         # functions.includeFiles + the /api/(.*) -> /api/index rewrite
  requirements.txt    # deps for the Python function (fastapi, pyyaml, httpx, jsonschema)
  package.json        # "vercel-build" copies the repo pieces the function needs into api/_bundle
  api/
    index.py          # ASGI entrypoint the Python function runs
    _bundle/          # generated by vercel-build, gitignored: data/, schema/, esp_atlas_core/, esp_atlas_api/
  app/, components/, lib/   # the Next.js app
apps/api/   # FastAPI app (esp_atlas_api.main:app) — the real route table
apps/core/  # esp_atlas_core — search/wizard/validate/index-build/facets, no HTTP
```

## How the split works

- `npm run vercel-build` (declared in `apps/web/package.json`) runs `rm -rf
  api/_bundle && cp -r ../../data ../../schema api/_bundle/ && cp -r
  ../../apps/core/src/esp_atlas_core ../../apps/api/src/esp_atlas_api
  api/_bundle/ && next build`, so the serverless function ships with the same
  markdown dataset and Python packages used locally.
- `apps/web/vercel.json` declares `functions."api/index.py".includeFiles =
  "api/_bundle/**"` and rewrites `/api/(.*)` to `/api/index`.
- `apps/web/api/index.py` prepends `api/_bundle` to `sys.path`, sets
  `ESP_ATLAS_REPO_ROOT` to the bundle dir so `esp_atlas_core.paths` finds
  `data/` and `schema/`, **builds the SQLite index at import time** (Vercel's
  ASGI adapter never runs FastAPI's lifespan hook — see commit d2c2b49), then
  mounts `esp_atlas_api.main.app` under `/api`.

So `esp_atlas_api.main`'s own route table (`/health`, `/search`, `/wizard`,
`/parts`, `/parts/{id}`, `/facets`, `/validate`, `/docs`) is unchanged — it
resolves under `/api/*` here and under `/*` when run standalone (`uvicorn
esp_atlas_api.main:app`, used for local dev and the API's own test suite).

### Writable paths on a read-only function

The function's filesystem is read-only outside `/tmp`.
`esp_atlas_core.paths.resolve_db_path()` honors an explicit `ESP_ATLAS_DB_PATH`
override; absent that, it falls back to `/tmp/esp-atlas.db` whenever the
`VERCEL` env var is set (Vercel sets this automatically) or the repo root isn't
writable. The index is rebuilt from the bundled markdown on every cold start
(~94 records, well under a second).

### Frontend → API URL

Browser side, `apps/web/lib/api.ts` calls the API at `NEXT_PUBLIC_API_URL`,
which defaults to `/api` (same-origin) in production builds and
`http://localhost:8000` otherwise.

Server side (server-rendered part pages, `generateMetadata`, `sitemap.xml`),
`apps/web/lib/api-server.ts` needs an absolute URL and resolves, in order:
`API_INTERNAL_URL`, an absolute `NEXT_PUBLIC_API_URL`, then
`https://$VERCEL_PROJECT_PRODUCTION_URL/api` in production (or
`https://$VERCEL_URL/api` on previews), then `http://localhost:8000`. Every
server fetch has a 3 s timeout and a 1 h cache; if the function is cold or
unreachable the part page falls back to client-side fetching instead of
failing. Preview deployments behind Deployment Protection will hit that
fallback (server-to-server fetches get a 401) — expected.

## Environment variables

| Variable | Required | Purpose |
|---|---|---|
| `NEXT_PUBLIC_GA_ID` | No | GA4 measurement ID. Production builds default to `G-66L7SDXKJZ` when unset; set it to point at another property. Dev/preview builds send nothing unless set. |
| `NEXT_PUBLIC_SITE_URL` | No | Canonical site URL for metadata, sitemap and robots. Defaults to `https://esp-atlas.com`. |
| `NEXT_PUBLIC_REPO_URL` | No | Overrides the GitHub URL used for "edit on GitHub" / contribute links (`apps/web/lib/github.ts`). Defaults to `https://github.com/fcavalcantirj/esp-atlas`. |
| `NEXT_PUBLIC_API_URL` | No | Overrides the browser's API base URL. Leave unset in production — it defaults to `/api`. |
| `API_INTERNAL_URL` | No | Overrides the server-side API base URL (see above). Normally unnecessary on Vercel. |
| `GROQ_API_KEY` | No (future) | Groq API key for the grounded `ask()` chat layer (`esp_atlas_core.llm`). Not used by any current route. |
| `ESP_ATLAS_REPO_ROOT` | Set by `api/index.py` | Where `esp_atlas_core` looks for `data/`, `schema/`, `prompts/`. Only needed manually for non-standard layouts. |
| `ESP_ATLAS_DB_PATH` | No | Overrides where `esp-atlas.db` gets built/read. Defaults to `/tmp/esp-atlas.db` on Vercel. |

Never commit `GROQ_API_KEY` or any secret — set it in the Vercel project's
Environment Variables settings.

## Deploying

```bash
npm i -g vercel   # once
vercel login      # once
cd apps/web
vercel            # preview deploy
vercel --prod     # production deploy
```

Pushes to `main` deploy through the Vercel GitHub integration; the repo-level
CI (`.github/workflows/validate.yml`) gates PRs on schema validation, the full
pytest suite and a source-liveness check.

## Verifying a deployment

```bash
curl https://<your-deployment>/api/health
curl https://<your-deployment>/api/facets
curl "https://<your-deployment>/api/search?q=zigbee"
curl https://<your-deployment>/api/parts/xiao-esp32c6
curl -s https://<your-deployment>/parts/xiao-esp32c6 | grep -o '<title>[^<]*'   # server-rendered title
curl https://<your-deployment>/sitemap.xml
```

`/api/health` returns `{"status": "ok", "count": <n>}` once the function has
built its SQLite index from the bundled `data/` on cold start.

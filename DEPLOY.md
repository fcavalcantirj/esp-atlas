# Deploying esp-atlas

esp-atlas ships as a **single Vercel deployment**: the Next.js frontend
(`apps/web`) and the FastAPI backend (`apps/api`, `esp_atlas_api.main:app`)
same-origin, with the backend served as a Vercel Python serverless function
under `/api`.

## Layout

The Vercel project's **Root Directory is `apps/web`** — Vercel detects Next.js
there and bundles only files under it, so the Python function and everything it
needs are co-located inside `apps/web`:

```
apps/web/
  vercel.json         # functions.includeFiles + the /api/(.*) -> /api/index rewrite
  requirements.txt    # deps for the Python function (fastapi, pyyaml, httpx, jsonschema)
  package.json        # "vercel-build" copies the repo pieces the function needs into api/_bundle
  api/
    index.py          # ASGI entrypoint the Python function runs
    _bundle/          # generated by vercel-build, gitignored: data/, schema/, esp_atlas_core/, esp_atlas_api/
  app/, components/, lib/   # the Next.js app
apps/api/   # FastAPI app (esp_atlas_api.main:app) — the real route table
apps/core/  # esp_atlas_core — search/wizard/validate/index-build/facets, no HTTP
```

## How the split works

- `npm run vercel-build` (declared in `apps/web/package.json`) runs `rm -rf
  api/_bundle && cp -r ../../data ../../schema api/_bundle/ && cp -r
  ../../apps/core/src/esp_atlas_core ../../apps/api/src/esp_atlas_api
  api/_bundle/ && next build`, so the serverless function ships with the same
  markdown dataset and Python packages used locally.
- `apps/web/vercel.json` declares `functions."api/index.py".includeFiles =
  "api/_bundle/**"` and rewrites `/api/(.*)` to `/api/index`.
- `apps/web/api/index.py` prepends `api/_bundle` to `sys.path`, sets
  `ESP_ATLAS_REPO_ROOT` to the bundle dir so `esp_atlas_core.paths` finds
  `data/` and `schema/`, **builds the SQLite index at import time** (Vercel's
  ASGI adapter never runs FastAPI's lifespan hook — see commit d2c2b49), then
  mounts `esp_atlas_api.main.app` under `/api`.

So `esp_atlas_api.main`'s own route table (`/health`, `/search`, `/wizard`,
`/parts`, `/parts/{id}`, `/facets`, `/validate`, `/docs`) is unchanged — it
resolves under `/api/*` here and under `/*` when run standalone (`uvicorn
esp_atlas_api.main:app`, used for local dev and the API's own test suite).

### Writable paths on a read-only function

The function's filesystem is read-only outside `/tmp`.
`esp_atlas_core.paths.resolve_db_path()` honors an explicit `ESP_ATLAS_DB_PATH`
override; absent that, it falls back to `/tmp/esp-atlas.db` whenever the
`VERCEL` env var is set (Vercel sets this automatically) or the repo root isn't
writable. The index is rebuilt from the bundled markdown on every cold start
(~94 records, well under a second).

### Frontend → API URL

Browser side, `apps/web/lib/api.ts` calls the API at `NEXT_PUBLIC_API_URL`,
which defaults to `/api` (same-origin) in production builds and
`http://localhost:8000` otherwise.

Server side (server-rendered part pages, `generateMetadata`, `sitemap.xml`),
`apps/web/lib/api-server.ts` needs an absolute URL and resolves, in order:
`API_INTERNAL_URL`, an absolute `NEXT_PUBLIC_API_URL`, then
`https://$VERCEL_PROJECT_PRODUCTION_URL/api` in production (or
`https://$VERCEL_URL/api` on previews), then `http://localhost:8000`. Every
server fetch has a 3 s timeout and a 1 h cache; if the function is cold or
unreachable the part page falls back to client-side fetching instead of
failing. Preview deployments behind Deployment Protection will hit that
fallback (server-to-server fetches get a 401) — expected.

## Environment variables

| Variable | Required | Purpose |
|---|---|---|
| `NEXT_PUBLIC_GA_ID` | No | GA4 measurement ID. Production builds default to `G-66L7SDXKJZ` when unset; set it to point at another property. Dev/preview builds send nothing unless set. |
| `NEXT_PUBLIC_SITE_URL` | No | Canonical site URL for metadata, sitemap and robots. Defaults to `https://esp-atlas.com`. |
| `NEXT_PUBLIC_REPO_URL` | No | Overrides the GitHub URL used for "edit on GitHub" / contribute links (`apps/web/lib/github.ts`). Defaults to `https://github.com/fcavalcantirj/esp-atlas`. |
| `NEXT_PUBLIC_API_URL` | No | Overrides the browser's API base URL. Leave unset in production — it defaults to `/api`. |
| `API_INTERNAL_URL` | No | Overrides the server-side API base URL (see above). Normally unnecessary on Vercel. |
| `GROQ_API_KEY` | No (future) | Groq API key for the grounded `ask()` chat layer (`esp_atlas_core.llm`). Not used by any current route. |
| `ESP_ATLAS_REPO_ROOT` | Set by `api/index.py` | Where `esp_atlas_core` looks for `data/`, `schema/`, `prompts/`. Only needed manually for non-standard layouts. |
| `ESP_ATLAS_DB_PATH` | No | Overrides where `esp-atlas.db` gets built/read. Defaults to `/tmp/esp-atlas.db` on Vercel. |

Never commit `GROQ_API_KEY` or any secret — set it in the Vercel project's
Environment Variables settings.

## Deploying

```bash
npm i -g vercel   # once
vercel login      # once
cd apps/web
vercel            # preview deploy
vercel --prod     # production deploy
```

Pushes to `main` deploy through the Vercel GitHub integration; the repo-level
CI (`.github/workflows/validate.yml`) gates PRs on schema validation, the full
pytest suite and a source-liveness check.

## Verifying a deployment

```bash
curl https://<your-deployment>/api/health
curl https://<your-deployment>/api/facets
curl "https://<your-deployment>/api/search?q=zigbee"
curl https://<your-deployment>/api/parts/xiao-esp32c6
curl -s https://<your-deployment>/parts/xiao-esp32c6 | grep -o '<title>[^<]*'   # server-rendered title
curl https://<your-deployment>/sitemap.xml
```

`/api/health` returns `{"status": "ok", "count": <n>}` once the function has
built its SQLite index from the bundled `data/` on cold start.

## Jr's merge switches (2026-11-17)

Jr merges its own demand PRs (`jr/research-*`) through the `demand-canary` job in `validate.yml` when two
switches allow: `jr/autonomy.json` `demand_automerge: true` (a reviewed PR) and the repository variable
`JR_DEMAND_AUTOMERGE` not set to `0`. **Stop it instantly:** `gh variable set JR_DEMAND_AUTOMERGE --body 0`
(repo settings → Variables also works); no PR needed. Re-enable by deleting the variable or setting `1`.
Optional repository secret `ESPATLAS_JR_TOKEN` (the bot's PAT): with it the canary's merge is made by the
bot and triggers main's workflows like a person's merge; without it the workflow token merges and main's
push-triggered runs do not fire for that merge (the PR's checks at the same head stand). `tick_automerge` /
`JR_TICK_AUTOMERGE` is the same pattern for review-routed tick PRs (`tick-canary`, four a day, every added
recipe's PASS receipt re-verified live by `receipt-guard`); `code_automerge` / `JR_CODE_AUTOMERGE` is the
code canary (`.github/workflows/agent-review.yml`: the agent reviewer's PASS at the exact head, one merge an
hour). The review runs on the runner's subscription delegate first (`jr/agent_review.py once`, hourly; the
job is the runner operator's, like the heal launcher) and falls back to Actions with the repository secret
`ANTHROPIC_API_KEY` only when the delegate reports its lane down, at most 3 a day (label `review-fallback`).
**What pays for the fallback (2026-11-20).** The Console organization behind that key holds two balances: the
purchased one, and the plan's monthly API credit (Console, Billing, "Promotional credits"; refilled each
billing cycle, no rollover). The monthly credit pays for the Claude API and the Agent SDK, not for Claude Code,
and Anthropic bills `anthropics/claude-code-action` as Claude Code. The fallback therefore runs `claude -p`
directly, which is billed as Agent SDK usage
([what the credits cover](https://platform.claude.com/docs/en/about-claude/api-credits-for-subscribers),
[help article](https://support.claude.com/en/articles/17154008-monthly-api-credits-for-max-ultra-and-team-plans)).
A refusal reads `billing_error` / "Credit balance is too low" in the review step's log, which prints the
result's error and cost. The Console's "Spend limits" page is a ceiling, not a balance: a workspace limit
caps what this lane may spend in a month.
Stop it: `gh variable set JR_CODE_AUTOMERGE --body 0`. Stop the tick canary: `gh variable set JR_TICK_AUTOMERGE --body 0`.

## Deploy only when the site changed (2026-11-21)

`apps/web/vercel.json` sets `ignoreCommand: bash scripts/ignore-build.sh` (Vercel's Ignored Build Step: exit 0
skips the deployment, exit 1 builds). The script skips a deployment only when nothing the site is built from
changed since the last successful deployment of the branch (`VERCEL_GIT_PREVIOUS_SHA`): `apps/web/`,
`data/`, `schema/`, `apps/core/src/`, `apps/api/src/` and the root `llms.txt`. Every doubt builds.

Why: each new deployment starts with an empty page cache (Vercel's ISR documentation), and Jr's hourly
bookkeeping merges were deploying production about 40 times a day. Uncached pages answer in 2-4 s, and Google
held back crawling new pages ("expected to overload the site"): 3 of the 38 firmware pages added in November
were indexed. A new path the site starts reading at build time must be added to the script's list (its tests
in `apps/web/lib/ignore-build.test.ts`).

## Hourly GitHub counts

Stars and forks are refreshed by the `hourly GitHub counts` workflow
(`.github/workflows/runtime-popularity.yml`), which publishes one file,
`popularity.json`, on the `runtime-popularity` branch; the API reads it over HTTPS
(`apps/api/README.md`). The workflow has **no `schedule:` trigger**: GitHub's cron
dropped most hourly slots, so an operator-run OS timer on an always-on host invokes
it instead, through `scripts/counts-dispatch.sh`.

The dispatcher needs `gh` (logged in with the `repo` scope), `flock`, `jq`,
`curl` and `timeout`. One invocation makes at most one dispatch
(`gh workflow run runtime-popularity.yml --ref main -f publish=true -f source=...`),
skips the hour when a run is already queued or in progress, waits (bounded) for the
run to finish, reads back the data-branch commit and `published_at`, and appends one
JSON line to its receipts file (default `$XDG_STATE_HOME/esp-atlas-counts/receipts.jsonl`).
Exit codes: `0` success or skipped, `1` dispatch failed, `2` run missing or failed,
`75` another invocation holds the lock. All knobs are environment variables,
documented at the top of the script.

Suggested systemd user units on the host (the only place host paths live):

```ini
# esp-atlas-counts.timer
[Timer]
OnCalendar=*-*-* *:07:00 UTC
AccuracySec=30s
Persistent=true
[Install]
WantedBy=timers.target

# esp-atlas-counts.service
[Service]
Type=oneshot
Environment=COUNTS_SOURCE=host-timer
ExecStart=/path/to/checkout/scripts/counts-dispatch.sh
TimeoutStartSec=8min
```

Operate it with:

```bash
systemctl --user enable --now esp-atlas-counts.timer     # start
systemctl --user disable --now esp-atlas-counts.timer    # STOP: no more hourly dispatches
systemctl --user list-timers esp-atlas-counts.timer      # next / last firing
```

Every run's name says who asked for it: `counts (host-timer)` is automation,
`counts (manual-testing)` a hand-run test. Run a test by hand with
`COUNTS_SOURCE=manual-testing scripts/counts-dispatch.sh`, never with the timer's
label. Publication also requires the repository Actions variable
`POPULARITY_RUNTIME_ENABLED=1`; setting it to `0` skips publish requests while the
timer keeps running, which is the GitHub-side stop.
